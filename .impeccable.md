## Design Context

### Users
Mostly solo librarians, archivists, and students (often doing a class assignment). They work alone at a desk with the docs open next to four or five other apps: GitHub on the web, GitHub Desktop, VS Code, the terminal, and a browser. Most are new to Git, the command line, and static sites. Many are nervous about breaking something, and nobody is nearby to ask. The job is to get a real digital collection website live from their own metadata, then come back later to find one specific step.

### Brand Personality
Patient, steady, bookish. The docs should feel like a calm reference librarian sitting next to you. It never rushes, assumes nothing, and openly says when something is annoying ("It's super annoying! We know!"). The emotional goals are reassurance and the quiet confidence of "I did that right."

### Aesthetic Direction
- Light theme by default (daytime desk work, read side by side with apps), with a considered dark mode.
- Anchored to CollectionBuilder red (#BF1722 ≈ oklch(0.52 0.19 25)) used sparingly, with warm-tinted paper neutrals and black for the brand header.
- Typography leans toward reading and accessibility: Atkinson Hyperlegible (Next / Mono) for body and code, with a bookish serif for headings.
- Anti-references: generic SaaS docs gloss, dark "developer" aesthetic, and autoplaying, looping media that competes with the reader.

### Design Principles
1. **Always say where you are.** Each instruction names the app you should be in and what success looks like.
2. **Media serves the reader.** Nothing moves unless asked. Video and visuals are first-class choices, not footnotes.
3. **Chunk, then sequence.** Long procedures are grouped into a few phases with visible progress, and progress persists.
4. **Keep the happy path clean.** Warnings and troubleshooting sit beside the main path and are disclosed when needed, not mixed into every step.
5. **Do the busywork for them.** Fill in the user's own values (username, repo name, filenames) so they copy instead of translating.
